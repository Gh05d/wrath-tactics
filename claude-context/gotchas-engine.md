# Engine: Evaluator, Validator, Executor, Trackers

Operative rules for `TacticsEvaluator`, `ActionValidator`, `CommandExecutor`, `PlayerCommandGuard`, `ActiveRuleTracker`, activatables, and blueprint infrastructure. IL evidence and incident reports: [`../docs/wrath-api-deep-dive.md`](../docs/wrath-api-deep-dive.md).

## Commands & Trackers

- **Never call `owner.Commands.Run` directly in `CommandExecutor` — route through `RunVerified`**: the engine can silently DISCARD the command instead of slotting it (`CanRunCommand` veto on unconscious/`CantUseStandardActions`, or `TryMergeInto` folding a same-Ability `UnitUseAbility` into a running `PreviousCommand`). A discarded command stays `IsStarted=false`/`IsFinished=false` forever — tracking it wedged `ActiveRuleTracker`'s gate until combat end (1.17.4 "rules randomly stop firing" bug). `RunVerified` checks `Commands.Raw` slot residency and returns the live in-flight command (merged occupant on merge, null on veto).
- **`PlayerCommandGuard`** reference-tracks `Commands.Run` from `CommandExecutor`; gates eval on foreign active casts (Standard slot or `Commands.Queue`, `UnitUseAbility` only, **AI-issued commands excluded via `cmd.AiAction != null`** — `AiBrainController.SelectAction` sets it before `Run`, a player click never has one; the old `Brain.AutoUseAbility` blueprint comparison could not tell the player's explicit Burning Arc from the AI's re-issued one and let rules override the player, v1.30) and, since 1.30, on a **player ground-click walk**: an unfinished foreign `UnitMoveTo` in the Move slot with `AiAction == null && !AiCanInterruptMark` (the engine marks its own formation/return moves, the party AI's moves carry an `AiAction`). Any command of ours would cancel that walk — Move rules replace it, Standard rules remove it via the paired-slot rule (deck 2026-09-16: `ExecuteCastSpell` killed 5 player walks). Don't widen beyond these — each constraint exists to fix a specific over-block regression. ([deep-dive](../docs/wrath-api-deep-dive.md#playercommandguard-scope))
- **`ActiveRuleTracker` (DAO priority gate)**: tracks `(RuleListSource, entry.Id, UnitCommand)` per-unit; while tracked command is `!IsFinished`, `TryExecuteRules` skips lower-priority **Standard-slot** rules (since v1.29.0 — move/swift/free rules are exempt, see the slot bullets below). Separate from `PlayerCommandGuard` (foreign casts vs. own commands). Toggles / `ThrowSplash` / `DoNothing` don't replace the entry — `Clear`-on-any-success reintroduces the lower-priority-preempt bug. ([deep-dive](../docs/wrath-api-deep-dive.md#active-rule-tracker))
- **Rule priority = list/array position** (top-down eval in `TacticsEvaluator.TryExecuteRules`). There is NO `Priority` field — it was vestigial (set at creation, never read) and removed; `RuleEditorWidget.MoveRule` reorders the array, which IS the eval order. UI display order + session-log "Rule N" both equal the array index.

- **Action slots are separate arrays, but Move and Standard are a PAIR.** `UnitCommands.m_Commands` is indexed by `UnitCommand.CommandType` (`Free = 0, Standard = 1, Swift = 2, Move = 3`). `Run` calls `InterruptAndRemoveCommand(cmd.Type)` and that one-argument overload forwards to `InterruptAndRemoveCommand(type, alsoPaired: true)`, which removes the Move slot for a Standard command and the Standard slot for a Move command — pending OR running (IL-verified 2026-09-09 after the 1.29.0 design assumed "same slot only" and shipped on it). Swift and Free are independent. Consequence: a Move ability issued while a cast waits or runs in Standard deletes the cast. Since v1.29.0 `TacticsEvaluator` walks the full rule list and applies the `ActiveRuleTracker` priority gate only to rules `ActionSlots.IsGated` says are Standard. `ActiveRuleTracker.Record` is likewise called only for Standard rules, so the tracker's contents mean exactly what they always did.
- **Classify from `AbilityData.RuntimeActionType`, never `Blueprint.ActionType`.** `RuntimeActionType` folds in Quicken metamagic (Swift → Standard once the swift action is spent) and the `MythicAbilitiesAsMoveAction` flag (Standard → Move, and it self-checks `HasCooldownForCommand(Move)` before doing so). `ActionSlots.Classify` falls back to Standard when the slot is unresolvable, so a classification miss degrades to the old one-action-per-tick behavior instead of escaping the gate.
- **The per-tick slot budget is `bool[4]`, shared across the global and character rule lists.** Without it, two swift rules in one tick would destroy each other through `InterruptAndRemoveCommand(Swift)`. `ThrowSplash` claims Standard in the budget even though it bypasses `Commands.Run` — otherwise a thrown flask fires *on top of* a cast and an attack every tick. `ToggleActivatable` claims nothing — it issues no command — and is bounded by a separate per-tick `HashSet` of ability IDs instead: an "X on" and an "X off" rule on the *same* activatable can both match in one tick (mixed enemy group), and without that guard the lower rule silently overwrites the upper one, inverting configs that relied on the old first-match-wins tick end. Different activatables still both fire.
- **The non-Standard busy guard checks for `UnitUseAbility` only — never bare slot occupancy.** The Move slot is near-permanently filled by engine-issued `UnitMoveTo` (approach, formation), so a bare occupancy check would mean a move-action ability never fires while the unit is walking. Same over-block class as the `PlayerCommandGuard` regressions. Consequence by design: running a move-action ability mid-walk cancels the walk, exactly as clicking one does.
- **Two animated commands must never run at once on one unit — the engine does NOT serialise them (v1.29.0 regression, fixed 1.29.1).** `UnitCommandController.TickOnUnit` ticks slots in array order (Free, Standard, Swift, Move) and starts each unstarted command as soon as `HasCooldownForCommand` allows; the only cross-slot hold is Standard-waits-while-a-Move-`IsRunning`. A second `UnitUseAbility`/`UnitAttack` starting on the same `AnimationManager` releases the running action (`AnimationManager.Execute`, `ExecutionMode.Interrupted`), and `UnitCommand.Tick` then interrupts the first command with the Owlcat-log error `Animation … is done but not acted for Unit[…]` — the cast never lands, no action is spent, the rule cooldown is already burnt. Concretely: cast [Standard] + Cackle [Move] issued in one tick ⇒ both start in the same frame ⇒ cast dies. `ActionSlots.CheckConflict` (pure, tested) + `TacticsEvaluator.HasCrossSlotConflict` block every overlap with three deliberate exits: **Move over an ENGINE-issued Standard command** (auto-attack in any state, or a still PENDING `Brain.AutoUseAbility` cast; `PlayerCommandGuard.IsOurs == false`) is allowed — `Run(Move)` removes it via the paired-slot rule, which is exactly what clicking the ability does, and the party AI re-issues its own command afterwards. A foreign cast that has already STARTED is `Running` (wait): `Run(Move)` over a casting unit does not remove it but queues behind it and sets `InterruptAsSoonAsPossible`, which `TickCommand` honours during the wind-up — deck 2026-09-16, 10 of 10 Cackles killed the AI's Ray of Frost unacted; **Move over an OWN Standard command** is always `PairedOwn` (the Run would delete our cast — the third deck test showed 100 % Evil-Eye loss under the earlier cooldown-margin heuristic); **Swift over a pending Standard** with more than 2.5 s cooldown left is allowed (Swift is not paired, but a running Swift does not hold Standard back, so the cooldown must outlast the swift animation). Log lines: `unit busy — own X running in Standard` / `own X pending in Standard — a Move command would cancel it (paired slot)` / `foreign X in Standard still approaching its target`; the allowed Move case traces `Move will cancel foreign X in Standard`.
- **`UnitCommands.Run(cmd)` cancels every unstarted command that is still walking into range.** IL-verified: after slotting, `Run` loops over `Raw` and calls `Interrupt(true)` on each other command with `!IsStarted && !IsUnitCloseEnough()` whenever `cmd` is Standard or Move (Swift/Free only if `cmd` itself is not close enough). So a pending Standard whose *cooldown* would justify a Move overlap is still not safe while its executor is approaching the target — our Move kills it, the slot empties, and `AiBrainController.TickBrain` (which only skips units holding a command with `AiCanInterrupt == false`) fills it with the party AI's default attack, i.e. `Brain.AutoUseAbility` (`BlueprintAiAttack.CreateCommand`). Deck 2026-09-08: Cackle over an approaching Evil Eye ⇒ Evil Eye `ended: Interrupt` 8/9 times, Ray of Frost in the slot. `CheckConflict` therefore takes `occupantApproaching` (= `!IsStarted && !IsUnitCloseEnough()`) and returns `SlotConflict.Approaching` before any cooldown reasoning.
- **`UnitCommands.Run` QUEUES instead of slotting when the unit is busy — and a queued command is a real command.** IL-verified (`TryUseSpecialHandlers` → `TryAddToQueueInsteadOfRunImmediately`): the new command goes to `Commands.Queue` when (a) any slot holds a command with `IsInterruptible == false` (a `UnitUseAbility` whose `ExecutionProcess.IsEngageUnit` — a cast in progress — or any command in its post-act animation tail), or (b) the occupant of our slot (or the Standard↔Move paired slot) `IsRunning` on the *same target* and our command `IsUnitCloseEnough()` — the melee-caster case: auto-attack on the treant, our Shocking Grasp on the treant. In both cases the engine sets `occupant.InterruptAsSoonAsPossible = true` and `RemoveFinishedAndUpdateQueue` runs the queued command (`fromQueue=true`) once its slot AND paired slot are empty. That is exactly what a player click does in the same situation, so `RunVerified` treats a queued own command as issued (DEBUG `Commands.Run queued X … behind Y — engine runs it when the slot frees`), tracks it, and the cooldown is stamped. Danger: **every `Run()` without `doNotClearQueue` calls `m_Queue.Clear()` first** — the player, the party AI or our next rule can make a queued command vanish unstarted. Both trackers therefore test residency with the engine's own `Commands.ContainsOrQueued(cmd)` (slot for its type OR queue): `ActiveRuleTracker.GetActive` drops a dead entry, `PlayerCommandGuard` purges it with INFO `own X vanished before starting (slot/queue cleared)`. The WARN `discarded … (engine veto)` is now reserved for the real vetoes (`CanRunCommand`) and same-slot merges. Two more consequences, both seen on the deck: **our own next `Run()` clears our own queued command** (Cackle issued in the same tick as a queued Evil Eye wiped it) — `HasCrossSlotConflict` therefore treats any own command in `Commands.Queue` as a hard conflict for every command-issuing rule (`unit busy — own X queued in Standard (any new command would clear the queue)`); and an issued command has already stamped its rule cooldown even if it never acts — `TacticsEvaluator.RefundVanishedCommands` keeps `(unit, command, cooldownKey)` until the outcome is known and refunds via the pure `IssuedCommandPolicy.Classify`: **finished without `IsActed`** (player move order cancelled the pending cast, higher rule pre-empted it mid-windup, dead target) or **neither started nor `ContainsOrQueued`** (queue wiped) ⇒ cooldown removed, INFO `… command ended Interrupt without acting — cooldown refunded` / `… vanished before starting — cooldown refunded`. The engine charges the action at the act point (`TickCommand` → `SpendAction` after `IsActed`), so "acted" is the exact line between spent and free; a full attack interrupted after its first swing stays spent.
- **A player click can sit in `Commands.Queue`, invisible to a slot-only foreign check.** Player clicks while the unit is auto-attacking or mid-cast are queued by the same rule, and our next `Run()` would clear the queue — i.e. silently overrule the player. `PlayerCommandGuard.HasForeignActiveCommand` therefore also scans the queue for a foreign Standard `UnitUseAbility` (same filters: not ours, not `Brain.AutoUseAbility`) and stands down (TRACE `Foreign queued cast detected`).
- **Reactive tick (v1.30): an own command ending forces the next Update to evaluate.** `CommandDiagnostics.HandleUnitCommandDidEnd` → `TacticsEvaluator.RequestTick` (sets `forceNextTick`). Reason: the party AI fills a freed Standard slot within one frame (default action started 37 ms after Cackle ended, deck 2026-09-16) while the evaluator polls every 3 s; without the reactive tick the right-click default action wins every standard action that follows a Move rule, and cast → cackle → cast chains lose a tick per link. Bounded by own command ends **that acted** (`IsActed || Result == Success`) and by a 0.5 s floor between reactive ticks (`ReactiveTickMinSpacingSeconds`): an unacted end + cooldown refund + immediate re-tick is a frame-rate loop (856 Misfortunes in one fight when the hex could not target the already-hexed treant). Do not extend it to foreign command ends — that would make the evaluator tick at the AI's 0.3 s re-issue cadence.
- **`CommandDiagnostics` gives frame-accurate command lifecycle for party units.** `IUnitCommandStartHandler/ActHandler/EndHandler` on the EventBus (DEBUG `own|foreign X [slot] started; also running: …` / `acted` / `ended Result (acted=…)`) plus a Harmony prefix on `UnitCommand.Interrupt(bool)` that logs the interrupter's engine frames (INFO for our commands: `… interrupted (started=…, acted=…) by UnitCommands.Run <- CommandExecutor.RunVerified <- …`). This is the tool for "who killed my cast" — the tick-granular evaluator log cannot answer it.
- **Engine action budget gates every command-issuing rule (v1.30, `ActionSlots.ActionSpent`).** `HasCooldownForCommand(slot)` is the engine's per-round verdict; the RTWP `SpendAction` books a standard action as `StandardAction = 6 − t` **plus `MoveAction = 3`**, a move action as `MoveAction += 3`, a swift as `SwiftAction = 6` (so after a cast the move action frees 3 s later, and `HasMoveAction()` = "one move left after a standard, else two"). A rule whose slot is spent AND whose remaining cooldown exceeds `TickIntervalSeconds` is skipped (`<Slot> action spent (2.7s left)`, no cooldown stamp); shorter remainders may still buffer so the command starts on time. Before 1.30 Standard commands always buffered — and a buffered Standard blocks every Move rule via the paired-slot rule for the whole cooldown, which is why "Cackle never fires without rule cooldowns" (Nexus, 1.29.1). The budget is what makes Move/Swift rules land in the same round as a Standard rule regardless of list order; list order still decides WHICH rule of a slot type fires. `Cooldown.{StandardAction,MoveAction,SwiftAction}` are the remaining seconds.
- **`UnitCommand.Result` (`None=0, Fail=1, Interrupt=2, Success=3`) is the only record of whether an issued command acted.** `PlayerCommandGuard.HasForeignActiveCommand` logs it when purging our finished commands (`own <ability> [<slot>] ended: Interrupt`). A smoke test that only checks `EXECUTED` lines proves issuance, not effect — v1.29.0 shipped that way. `IUnitCommandEndHandler.HandleUnitCommandDidEnd(UnitCommand)` exists on the EventBus if a push-style hook is ever needed.

- **`MoveToTarget` (v1.30) is a `UnitMoveTo(destination, approachRadius = MaxMeters(bracket), distanceXZ: true)` in the Move slot.** Validator (`ActionValidator.MoveToTarget.cs`): `State.CanMove`, resolvable unit/point target, `RangeBrackets.Beyond(distance, MoveWithin)`; "already within" is a silent fall-through (`CanMoveToTarget: … already within Short`), so the rule re-evaluates every tick and follows a moving target until the bracket holds. Not animated, but it runs through `HasCrossSlotConflict` (`ActionSlots.NeedsCrossSlotCheck`) because `Run(Move)` removes an own pending/running Standard command; over the engine's auto-attack it fires and cancels it, the party AI re-attacks afterwards (same as a player move click). `UnitMoveTo` does its walking BEFORE `Start` (`TickApproaching`; Start = arrival) and never sets `IsActed`; the cooldown refund therefore treats `Result == Success` as acted for every command class, and the validator declines to re-issue while an own walk to within 1.5 m of the same destination is still resident (`walk in progress`) — re-issuing every tick interrupted it unstarted and restarted the path.

## Validation & Execution

- **Unit-targeted casts of abilities WITHOUT a point target must pass `AbilityData.CanTarget(new TargetWrapper(unit))`** (v1.30, `ActionValidator.CanExecute`; point-capable spells such as Fireball may carry no unit-target flags and are cast at the unit's position, so they keep the old path): `ResolveCastSpellChain` only proves the ability is castable, not that THIS target is legal; hexes carry a 24 h per-target restriction (`IAbilityTargetRestriction`) and the engine enforces it only after the command started (`UnitUseAbility.OnTick` self-interrupt, unacted). Same check `CanUseItem` already had.
- **Validator strictness is load-bearing**: new `ActionType` must validate up-front in `ActionValidator.CanExecute` (incl. `AbilityData.IsAvailable`). Chain-capable types (CastSpell, CastAbility) MUST route through `ResolveCastSpellChain` — single-GUID validation misses the chain. ([deep-dive](../docs/wrath-api-deep-dive.md#validator-strictness))
- **Cast fallback chain spans CastSpell + CastAbility (since 1.15)**: `ResolveCastSpellChain` is the authoritative validator + executor entry point for both Cast types — never re-introduce single-GUID validation on either branch (breaks rule fall-through when primary unavailable). ([deep-dive](../docs/wrath-api-deep-dive.md#cast-fallback-chain))
- **`ResolvedTarget` wrapper**: `TargetResolver.Resolve` returns a struct (Unit XOR Point, both null = `None`). `ActionValidator.CanExecute` and `CommandExecutor.Execute` branch on `IsPoint`. `ResolvedTarget.None` fails validation — no silent self-cast fallback.
- **`TargetWrapper` dual ctors**: `(UnitEntityData)` for unit, `(Vector3 point, float? orientation = null, UnitEntityData unit = null)` for point. `UnitUseAbility.CreateCastCommand(AbilityData, TargetWrapper)` takes either.
- **Cast fires once per round, AttackTarget full-attacks**: `CastSpell`/`CastAbility` issue `UnitUseAbility` — a standard action, ONE activation per command. `AttackTarget` issues `new UnitAttack(target, null)` — the same command class the engine's auto-engage uses, i.e. a full attack with iteratives. Kinetic blasts are weapons under the hood: blast as in-game default attack + rule action AttackTarget ⇒ ~2 blasts/round at BAB 6+ (user-corroborated, Nexus v1.25.0 thread; not IL-traced end-to-end). Triage: "ability only fires once per round" reports → recommend AttackTarget, not Cast.

## Activatables

- **ActivatableAbility API**: has `TryStart()` but NO `TryStop()`. Deactivate via `IsOn = false`.
- **Target-aware `ActivatableAbility`s exist** (Mount is canonical): `TryStart()` sets `IsWaitingForTarget=true`, then engine expects a target-unit click. Current `ToggleActivatable` action only handles self-targeted toggles and CANNOT drive Mount end-to-end. ([deep-dive](../docs/wrath-api-deep-dive.md#mount-ability))

## Tick & Timing

- No per-round EventBus events in RTWP mode — use `Game.Instance.Player.GameTime` in `Update()`.
- **Continuous out-of-combat tick (since 1.7.0)**: `TacticsEvaluator.Tick` runs in both states. Out-of-combat interval = `TacticsConfig.OutOfCombatTickIntervalSeconds` (default 2 s, JSON-only), pre-filtered through `RuleEnabledOutOfCombat`. Cooldown clock = `CooldownRounds * 6f` against `GameTime.TotalSeconds`; same clock in RTWP and turn-based. ([deep-dive](../docs/wrath-api-deep-dive.md#continuous-out-of-combat-tick-since-170))

## Blueprint Infrastructure & Misc

- **Blueprint enumeration**: `ResourcesLibrary.s_BlueprintsBundle` doesn't exist (binary pack, not AssetBundle). Use `ResourcesLibrary.BlueprintsCache.ForEachLoaded((guid, bp) => ...)`. **`ForEachLoaded` is misnamed**: it iterates the FULL index (`m_LoadedBlueprints`, ~236k entries) and passes `entry.Blueprint` **with no null filter** (verified IL) — `bp` is `null` for any blueprint not yet lazily loaded. So a `bp is BlueprintBuff` check silently skips every unloaded buff; callers see only the session's already-touched subset. To list ALL of a type, force-load first: iterate `m_LoadedBlueprints.Keys` + `BlueprintsCache.Load(guid)` (publicizer-accessible) — but that's ~236k loads (~79s, all resident; eviction via `RemoveCachedBlueprint` is destructive — drops the index Offset). The buff picker pays this once and persists metadata to disk. ([deep-dive](../docs/wrath-api-deep-dive.md#blueprint-full-enumeration))
- **Unit facing**: `UnitEntityData.OrientationDirection` is a public `Vector3` returning forward vector.
